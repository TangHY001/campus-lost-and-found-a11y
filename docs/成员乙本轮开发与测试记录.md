### 2026-11-09 联调前补测

独立 MySQL 实例中已通过真实 HTTP 登录、发布、重复提交、本人详情、编辑重审和下架。三轮发布请求各采一次样，约 144–159ms，不含上传。甲丙的联调要用同一个物品编号按以下顺序核对。

1. 学生登录并带图提交。记录物品编号，确认本人可看，访客看不到物品和图片。
2. 丙用管理员审核通过。访客按标题搜索，核对详情和图片都能打开。
3. 发布者修改标题并重新提交。访客再次用原编号访问，确认详情和图片已隐藏。
4. 再次通过审核后，用另一个学生账号发起认领。待确认时测试下架是否关闭申请。另建一条已确认认领的记录，核对拒绝下架。

公开查询已在本机独立库测过，每轮 1 万条虚构公开记录，分三批，每批同时发起 100 个查询，列表与关键词搜索各占一半。默认连接配置的直连复测中，300 次有 63 次返回正确结果、237 次在客户端 12 秒限时内未完成，正确且在 1500ms 内完成的为 0 次，未达到 98% 指标。连接池调到 40 并启用 JDBC 本地会话状态的对照组仍未达标，默认配置未采用该实验参数。保留原始结果于上一级 `.codex-review/member-b-2iq2q4gs/metrics.json` 和 `.codex-review/member-b-vy1ptdza/metrics.json`。这次测量未定位超时根因。

本机 MySQL 已启动并能用应用账号连接。检查时仍缺 V003 两个字段，需要用有 ALTER 权限的账号执行 V003。前端已监听 5173，后端待迁移后启动。

远端截至本轮检查仍停在 `38d43d6`，本地已生成可应用于该版本的 34 文件补丁，位置为工作区上一级 `.codex-review/member-b-integration.patch`。补丁通过 `git apply --check` 等效的临时暂存区检查，可供明天核对版本。常规 Git 提交仍从原分支整理。

本轮已接通：**带图发布 → 我的发布 → 修改后重新审核 → 主动下架**。查询和发布防重继续保留。

自动化验证使用另一套临时 MySQL 实例。正式手动检查前需要更新日常开发库，再启动前后端。

1. 在 VS Code 的 Database 中，用有建表权限的账号连接 `campus_lost_found`，完整执行一次 [V003](../database/migrations/V003__item_submission_key.sql)。程序账号 `lostfound_app` 没有 ALTER 权限。已有记录会保留。
2. 在 `backend` 目录用 JDK 21 运行 `mvnw.cmd spring-boot:run`。如果提示 8080 被占用，先结束旧后端。
3. 在 `frontend` 目录运行 `npm.cmd run dev`，浏览器固定使用 `http://localhost:5173`。
4. 登录，发布一条带 1～3 张 JPG/PNG 的信息。成功弹出“已提交”，按钮禁用；进入“我的发布”应看到待审核记录和图片。
5. 修改标题、替换或移除图片，再提交。状态应为待审核，版本号在后台递增。
6. 下架该信息，列表显示“已下架”，编辑入口消失。下架前有确认提示，下架后不能恢复。

检查后再整理 Git 提交：当前仍保留上一轮 B03 的两份暂存文件，本轮新增功能尚未全部暂存。仅关闭 `COMMIT_EDITMSG` 不会自动把本轮所有代码加入提交；应在“源代码管理”核对更改与暂存内容，再提交。未代替用户完成提交或推送。

公开浏览只展示已审核发布的信息。**审核按钮仍由丙实现**，本轮自动化测试用 SQL 夹具模拟审核后的状态，不能写成已与丙完成联调。检查“审核后公开、修改后隐藏、下架后隐藏”需在丙模块接入后再现场走一遍。

## 用软件工程课的说法解释这些测试

| 方法 | 本轮实际例子 | 判定 |
| --- | --- | --- |
| 黑盒等价类 | 合法 JPG/PNG、伪造文件、空文件；本人/他人/访客；不同物品状态 | 合法输入成功，不合法输入给出明确错误且不破坏原数据 |
| 黑盒边界 | 0 字节、2097153 字节；3 张和第 4 张；重复或溢出的图片编号；标题和描述长度 | 超过范围拒绝；三张有效图片可绑定 |
| 白盒分支 | 图片是否存在/归属本人/已绑定；认领未驳回/全部驳回；版本相同/过期；状态允许/终态 | 用例覆盖这些具体判断的两种结果；**未生成覆盖率报告，不能声称分支或路径覆盖率 100%** |
| 并发 | 两线程用相同编号发布；两线程用相同版本编辑 | 前者仅一条物品；后者仅一个成功、另一个 VERSION_CONFLICT |
| 回归 | 新增图片和修改后，重新执行账号、注册、个人资料、公开搜索、防重等全部后端测试 | 61 项通过；前端 23 项通过 |

## 联调时必须告诉队友

- 本轮为乙的管理流程补上 `/me/items`、`/me/items/{itemId}` 和“我的发布”入口。这两条查询在原分工中属于甲；本轮属于补充适配，联调时统一入口，避免甲再添加同路径造成重复映射。公共账号/会话基础仍归甲。
- 编辑按之前已审定的需求：FOUND 没有认领或认领全部 `REJECTED` 可以编辑；PENDING、CONFIRMED 等其他历史不允许。LOST 有线索历史不允许编辑。本轮已同步接口规范；请甲丙按同一口径接入。
- 乙写物品时先锁物品行。丙的审核、认领创建/确认、交接也需先锁同一物品行，再检查状态与版本，避免“编辑与认领同时成功”等跨模块冲突。跨模块并发尚未验证。
- 乙只在下架时原子关闭 PENDING 申请，保留历史；线索创建、留言、找回归档仍未实现，不将其列为乙已完成内容。
